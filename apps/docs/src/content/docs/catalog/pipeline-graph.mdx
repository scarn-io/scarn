This is the graph view that `scarn pipelines studio` renders locally. Here it runs over static fixtures instead of a live directory. Each fixture is written in TypeScript with `@scarn/sdk/pipelines`, and `scarn pipelines build` compiles it to the JSON document that `scarn pipelines publish` sends (see [Building Pipelines](/scarn/guides/pipelines/)). Open "View source" under any example to compare the two. The steps the examples use are listed [at the end of the page](#steps-used-by-these-examples).

At build time, `translateDocumentToGraph` (the `"."` export of `@scarn/pipeline-studio-ui`) turns each document into `{nodes, edges}`. The graph has a synthetic **Start** node for the `start` transition and one edge for each `next` and `catch` entry. Edges are labelled with their condition, `otherwise`, an `each` or `partial` marker, or the errors they catch. The same `PipelineGraphView` component the studio uses (its `"./view"` export) renders it in the browser. Drag to pan, scroll to zoom, and use the controls in the bottom-left corner to fit or reset the view.

## Conditional next

A step's `next` list is checked in order. The first transition whose `when` condition matches is taken, and the last entry, which has no `when`, is the fallback.

## Decision

A `wait` node with `"for": "decision"` pauses until a person picks one of its `actions`, optionally with a written body. Its result `{ action, body }` is branched on like a step's. Here `revise` needs a body and loops back to `proposeFix` with it as `feedback`, and `nodes.proposeFix.result` reaches back to the step's result once the fix is approved.

## Loop, retry and catch

A transition can lead back to the node it leaves from. `maxRuns` bounds the loop by raising `Scarn.MaxRunsExceeded`, which the `catch` edge sends to a `fail` node. `retry` doesn't appear on the graph, because a retry is a new attempt of the same node.

## Lanes

`each` starts one lane per file, with up to five running at once. Every lane runs `editFile` and then `reviewEdit`. Each review is a `partial` route into `approveReviews`, which merges them into one `reviews` list and runs once every lane has arrived. A person then approves or rejects the reviews, and the pipeline branches on `action`: open the PR, or fail.

## Every matching route

With `match: "all"`, every route that matches runs in its own lane. A route with no `when` always runs, and `otherwise` runs only when no conditional route matched. `writeFailingTest` is a partial merge of two of those lanes, and `summariseFindings` is the closing merge that waits for every lane that can reach it.
