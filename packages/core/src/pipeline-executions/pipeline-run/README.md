# Pipeline Run

A pipeline run executes one published pipeline version against one work item. The version's document (`@scarn/sdk/contracts/pipeline-document`) is the routing; the pure engine in `domain/engine/` decides, and the use cases in `application/` load state and write the decisions.

## Engine

`domain/engine/decide.ts` is `decide(document, runState, event, options) → commands`: a pure interpreter with no database access. It reads an in-memory copy of the run (`RunState` in `domain/engine/types.ts`, mirroring the tables below) and returns ordered commands that `advancePipelineRun` writes in one transaction. It uses the document schema, condition evaluator and reference resolver from `@scarn/sdk/contracts/pipeline-document` and `@scarn/shared-core/pipelines`. Its unit tests live in `tests/pipeline-executions/pipeline-run/unit/` and drive it through `RunSimulator` (`engine-harness.ts`).

## Tables

- `pipeline_runs`: status (`active`, `waiting`, `succeeded`, `failed`, `cancelled`), `end_node_id`, `error`. A run is pinned to `pipeline_graph_version_id` for its whole life.
- `node_visits`: one row each time the run enters a node, with how it got there (`from_visit_id` / `from_lane_group_id` and `transition`), its `input`, its `result` or `error`, and the engine's `routing` (which transition it checked and took, plus notes such as `branch_ambiguous`, and `overrules`: one entry per time a person overruled the visit's routes, with `from` and `to` (the routes taken before and after), `byUserId`, `at`, `reason` and the `missingArgs` they accepted; `taken` is always the current set). A step visit's `result` is its result Task's, or `{ conversationId, summary }` when a person ended its conversation (no result Task). A step visit's conversation is its Task's (`tasks.conversation_id`); the repo loads it onto the visit as a read-only `conversationId`. A rerun marks the old visits `superseded` and adds new ones; nothing is overwritten.
- `node_visits.task_id` (unique): a step visit's Task, created when the visit first queues work. Every attempt, retry or continuation of the visit is a run of that Task (`task_runs.number`, `reason`); the engine's `VisitTask.attemptNumber` is the run's `number`. This is the only link between a pipeline run and a Task. A visit's result run (`resultTaskId` in the read model) is derived on load: the visit's latest run, when the visit ended by that run succeeding.

**Task vs TaskRun.** A Task is the visit's one piece of work and holds the instructions, plus the node's `retry` and `maxTurns`. A TaskRun is one attempt at it, the thing a worker claims. Engine events, `VisitTask.taskId`, `CommandWriter` and conversation messages all use run ids.

- `lane_groups` / `lanes`: a transition with `each` fans out into one lane per item, and `match: "all"` into one lane per route taken; a later merge waits for the group. An `each` group's lanes are fixed, but an overrule can add lanes to an `all` group or cancel some of its lanes. A group whose spawning visit is superseded, or whose enclosing lane is cancelled, is dead: it no longer holds the run open.
- `node_visit_questions`: the question comments a visit waits on (`open`, `answered` or `not_needed`). The comment is an agent-authored work item comment written first; a comment is a question when a row here points at it.

`queued` and `running` are not stored. The read model splits an `active` run by its open visits' latest Tasks: `running` if any is claimed, else `queued`.

## Advancing

Every change goes through `advancePipelineRun(runId, event)`. In one transaction it locks the run row, loads the run, its visits, lanes, Tasks and questions, calls `decide`, and writes the returned commands in order (insert/update visits, queue Tasks, ask and update questions, update lanes and the run). It returns the run's completion, which the caller reports once the outermost transaction commits.

A queued Task's input is its step's resolved args and nothing else. The work item is not copied in: the agent reads it live with `scarn-get-work-item`.

## Waits

A `wait` node with `for: "decision"` lists its `actions` (each a `key`, a button `label` and whether a `body` is `required` or `optional`) and waits for `decideWaitVisit`. Its result is `{ action, body }`, and routes branch on `result.action`. A `wait` with `for: "reply"` posts one question comment (its `questions` arg, rendered by `domain/engine/questions.ts`) and waits on that question. Its result is `{ replied, body, commentId }`. When a visit closes unanswered (cancel, a failed lane or run, a rerun that supersedes it) its open questions become `not_needed`, and a later reply to them resumes nothing.

A step visit can wait too. When its Task yields (`task_waiting`, the agent's final message), the agent hands the conversation to a person: the Task has already posted the message into its own conversation (`tasks/README.md`), so the engine only makes the visit `waiting`, with a `question_cut` routing note when the message was over 10,000 characters. The step's `maxTurns` (default 2, 0 turns hand-offs off) is copied onto the visit's Task, which counts its own turns (`tasks/README.md`): a yield over it fails the Task, and the engine gets `task_failed` named `Scarn.MaxTurnsExceeded`, which the Task never retries. `conversation_replied` reopens the visit and queues the next attempt: `previousTaskId` is the latest yielded Task, the base is its work branch (else the visit's base branch), and there is no message, since the reply reaches the agent through the conversation. `conversation_ended` (a step with no result schema, ended by a person) succeeds the visit with `{ conversationId, summary }` and follows `next`. Both are ignored unless the visit is a waiting step visit with a conversation. A rerun's new visit has a new Task, so it starts again from the limit. Task events are only acted on for `active` visits, yielded Tasks count as finished (cancelling a waiting step visit cancels no Task), and yielded attempts don't count against the Task's `retry`.

When an `updateVisit` in the command writer (`advance-pipeline-run.ts`) ends a step visit (succeeded, failed, cancelled or superseded) it closes the visit's conversation, so the engine never has to. A run waiting on a step visit reports `waitingFor: "reply"`. The work item's comments are not touched.

Each `askQuestion` (and each hand-over, from the Task) also creates a `feedback_request` notification (`notifyWaitingForPerson`, `notifications/user-notification/`) in the same transaction, dispatched under the project's notification rules: audience `specific_users`, `payloadJson` `{ conversationId | questionId }`, one row per recipient (`recipient_user_id`), the recipients being the work item's creator and the run's `triggeredByUserId`. An agent message's notification carries its `taskId`; a question's has none. The in-app list shows a caller their own notifications plus the project-wide ones (a null `recipient_user_id`).

A conversation step is a step whose definition has no result schema. Its agent ends the step by itself or a person ends it with **Done**; either way the visit's result is `{ conversationId, summary }`. The Task side owns this (`tasks/task/application/on-task-ended.ts`): a succeeded schema-less run stores `{ conversationId, summary }` as its `resultJson` (the trimmed `summary` it reported), creating the conversation and linking it to the Task if the agent never handed over, and posts the summary as the closing agent message when it isn't empty. The conversation closes, and the Task's saved sessions are deleted, when the Task ends, not when the visit ends; a visit that ends while its Task waits on a person cancels that Task.

Events and their callers:

- `start`: `createPipelineRun`, on the active version or a given `version`.
- `task_succeeded` / `task_failed` / `task_waiting` / `task_cancelled`: sent by `pipelineTaskOutcomePort` in `task-and-advance.ts` when `onRunEnded` changes a Task's status; a timeout or abandoned lease is `task_failed` named `Scarn.Timeout` / `Scarn.HeartbeatTimeout`, and a yield with no turns left is `task_failed` named `Scarn.MaxTurnsExceeded`. The wrappers (`completeTaskAndAdvance`, `yieldTaskAndAdvance`, `pipelineTerminalTaskRunHandlers`) each run the task operation from `tasks/` with that port and, only when the run's Task is a visit's (`node_visits.task_id`), advances that run in the same transaction. `pipelineTerminalTaskRunHandlers` plugs the timeout and abandoned-lease handlers into claims and heartbeats.
- `task_waiting`: `yieldTaskAndAdvance` in `task-and-advance.ts`, behind `POST /tasks/:taskId/yields`. It saves the yielded run (with its work branch) before advancing, so the continuation a reply queues can start from that branch, and the event carries the yield's `message` (the run doesn't store it).
- `conversation_replied`: `conversation-and-advance.ts`, behind the conversation routes. `sendConversationMessageAndAdvance` (`POST /conversations/:id/messages`, `comments:create`) saves the person's message and, only when the conversation was `waiting_for_person`, advances the visit whose Task owns the conversation (`tasks.conversation_id`); a message while the reply is still pending joins that turn. `continueConversationWithoutReply` (`POST /conversations/:id/continue`, `executions:write`) posts a `system` message and sends it with `noReply`.
- `conversation_ended`: `endConversationAndAdvance` (`POST /conversations/:id/done`, `executions:write`), only on a conversation step (`CONVERSATION_STEP_HAS_RESULT_SCHEMA` otherwise). It posts a `system` message and sends the last agent message as `summary`. Continue and Done need the conversation `waiting_for_person` (`CONVERSATION_NOT_WAITING`); an event the engine ignores rolls the whole command back (`CONVERSATION_VISIT_NOT_WAITING`), through `withAdvance`'s `verify`.
- `decision_made`: `decideWaitVisit`, which records the action a person chose on a decision wait, with its body trimmed (blank becomes null). An action the node doesn't list, or a missing body the action requires, is rejected (`PIPELINE_RUN_DECISION_INVALID`); a visit that isn't waiting for a decision is rejected (`PIPELINE_RUN_VISIT_NOT_WAITING`).
- `question_answered`: `answerQuestionAndAdvance` (`comment-and-advance.ts`, `POST /pipeline-executions/:id/questions/:questionId/answer`), which saves the answer as a reply under the question's comment and answers with it; and `continueWithoutReply`, which answers with no reply. Only wait visits are answered; a question on a step visit is ignored. Both reject a question that isn't open, or whose visit isn't waiting (`PIPELINE_RUN_QUESTION_NOT_OPEN`), and roll back. A threaded reply posted through `POST /work-item-comments` is a plain comment and never answers a question.
- `rerun_from`: `rerunVisit`, and `sendVisitMessage` (a rerun whose new Task carries the message; code and MCP tool steps are rejected with `PIPELINE_RUN_MESSAGE_CODE_STEP`).
- `route_overruled`: `overruleVisitRoute` (`POST /pipeline-executions/:id/visits/:visitId/route`, `executions:write`), built by `buildOverruleEvent` (`overrule-route-event.ts`), which resolves the requested routes (by index, `otherwise`, target or label). The engine's checks (`domain/engine/overrule-checks.ts`) allow only a succeeded step visit, and only changes to routes the document marks `overridable` (`isRouteOverridable` in the SDK's `pipeline-document/routes.ts`). On `match: "first"` the engine supersedes the visit's descendants (as `rerun_from` does, minus the visit itself) and follows the new route. On `match: "all"` it cancels the removed lanes, adds lanes for the added routes to the same group, and supersedes every merge whose input changes so it fires again; untouched lanes keep running. A finished run reopens. Missing args refuse the overrule (`PIPELINE_RUN_ROUTE_ARGS_MISSING`) unless `acceptMissing`, which a code-step target never allows. `preview: true` runs `decide` in a transaction, summarizes the commands (`summarizeOverrule`) and writes nothing.
- `cancel`: `cancelPipelineRun` / `cancelPipelineExecutions`.

User commands go through `commandPipelineRun`, which checks `executions:write` on the run's project. Engine refusals (`DecideError`) become `PIPELINE_RUN_<CODE>` validation errors, and an unknown visit becomes a not-found. An answer needs only `comments:create`, the permission `createWorkItemComment` checks.

`withAdvance` (`task-and-advance.ts`) is the one helper the operation wrappers share: it opens the transaction, runs the operation (a Task outcome, a new comment, a conversation message), advances the run the outcome names, optionally checks the advance (`verify`, which throws to roll back), and reports a completion after commit when it owns the transaction. `commandPipelineRun` does the same for user commands.

`get-conversation.ts` reads a conversation with its visit and `endsWith` (`findings` with a result schema, `conversation` without), behind `GET /conversations/:id`, and lists a work item's conversations with their messages, loaded in one batch (`GET /work-items/:id/conversations`); both need `executions:read`. `GET /work-items/:id/questions` lists its questions with their body and who they wait on (`waitingOn`, `waitingOnYou`): the work item's creator and the person who started the run, while the question is open.

`comment-and-advance.ts` also guards question comments: `editWorkItemCommentGuarded` and `deleteWorkItemCommentGuarded` refuse while the comment's question is open (`WORK_ITEM_COMMENT_QUESTION_OPEN`). The dependency points from pipeline code to comments; `work-items/` stays unaware of runs.

## Failures

Retries belong to the Task (`tasks/README.md`): the node's `retry` is copied onto it, and `onRunEnded` queues retry runs itself without telling the engine. The engine only sees `task_failed` once the Task has stopped retrying, and it reloads a visit's runs from the database on each advance, so a retry run shows up as the visit's next attempt. A failed Task's error is the named error it stored, else `Scarn.StepFailed`. The first matching `catch` moves to its target with `error` in scope; else the lane or the run fails. Errors the engine raises itself (`Scarn.ArgsError`, `Scarn.ConditionError`, `Scarn.MaxRunsExceeded`) are never retried.
