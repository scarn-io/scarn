# Tasks

This domain contains the claimable unit of execution and the configuration it runs with.

Responsibilities in this domain include Task lifecycle state, claims and leases, liveness, the Task's result, logs and log archives, artifacts, agent sessions, task messages, and the task execution config a Task runs with.

Current entities in this domain include `task`, `task-run`, `task-artifact`, `task-log`, `agent-session`, `task-message` and `task-execution-config`.

## Vocabulary

- **Work item:** the user-facing unit of work (see `work-items/`), including sub work items. It is never called a "task" to the user.
- **Task:** one piece of work on a work item (`tasks`, `task/`). It holds the instructions, copied at creation: `kind` is `agent` (runs a `prompt`), `code` (runs an `entrypointJson`) or `mcp_tool` (calls one MCP tool, described by `toolCallJson`: server, tool, args template and the tool's schemas; no prompt or entrypoint, and no LLM), plus `resultSchemaJson`, `name`, `inputJson`, `taskExecutionConfigId` and the clocks. A pipeline step visit's Task also copies the node's `retryJson` and `maxTurns`; a standalone Task copies its step definition's `retry` as `retryJson`. `stepDefinitionId` records where the instructions came from. The Task is pipeline-unaware: pipelines point at it from above (`node_visits.task_id`). Nothing in `tasks/` imports `pipeline-executions/` or `pipeline-definitions/` application code. Its status follows its latest run; late events from older attempts cannot overwrite the current attempt's outcome.
- **TaskRun:** one claimable attempt at a Task (`task_runs`, `task-run/`). Runs are numbered from 1 per Task (`number`, unique per Task) and say why they started (`reason`: `initial`, `retry` or `continuation`). Claims, leases, liveness, results, logs, artifacts and agent sessions belong to the run. `TaskRunEntity` reads the instructions from its Task through a join and only writes run columns. `POST /tasks` creates a Task and run #1, or, on a blocked work item, a `waiting_for_work` Task with no run (or, when its concurrency group is full, a `waiting_for_concurrency_slot` Task with no run, or nothing; see Concurrency group); `GET /tasks/:taskId/runs` lists its runs oldest first.
- **Task name:** `tasks.name`, nullable. A Task created from a step copies the step's `name`; a standalone Task may set one. The worker's session title is the Task name, then the work item title, then the Task ID.
- **Task execution config:** what a step or Task **overrides** on top of the repo's own config (`.devcontainer/`, `.opencode/`, `.scarn/`): runtime (`devcontainer` / `managed` / `none`), env vars (each with `applies`: `agent`, `setup` or `both`), git mode, OpenCode MCP servers, and `cli` + `tool` health checks in one ordered list. A null field means the repo default.
- **Agent session:** one external agent session in one container, owned by one Task. A conversation that outlives a container is a chain of sessions sharing `conversationRootId`; `parentAgentSessionId` records subagent sessions.
- **`yielded`:** a Task status meaning the agent ended its turn and handed the conversation to a person. The Task owns the conversation (`tasks.conversation_id`, `conversations/`): `onRunEnded` hands over (`hand-over.ts`) when a yield leaves the Task `waiting_for_person`. It opens the conversation on the first hand-over and gives the floor back to a person after that, posts the message (cut by `agentMessageBody`) with the run's `task_run_id`, and sends a `feedback_request` to the work item's assignee and its creator (or, when it has neither, those of its nearest parent that has either; the system actor counts as no creator) and whoever started the Task (for a pipeline Task, the run's starter, found through `TaskPipelineRunPort`; `workItemWaitingOnUserIds`). Who a Task waits on isn't stored: while it is `waiting_for_person`, Task reads derive the same people from the work item's current assignee and creator (with the same parent walk, `work-items/work-item/infra/work-item-waiting-on-sql.ts`) and `tasks.started_by_user_id` (a pipeline Task copies the run's starter there) in `task/infra/task-waiting-on-sql.ts`, so a reassignment shows at once. A Task summary's `waitingOn` lists them, and `waitingOnYou` is true only for a viewer among them; the `waitingOnMe` filter, the inbox counts and the work item list's `waitingOnYou` count use the same expression. A yield is terminal for the run: a reply starts another run of the same Task (`reason` `continuation`).
- **`waiting_for_work`:** a Task status meaning its work item has an open blocker, so its next run isn't queued yet. `work-items/` calls `WorkItemEventsPort.mayHaveBecomeReady` when a create, close, reopen or block change may have freed an item; `di.ts` connects the port to the `AutomationRunner`, which first calls `startReadyWork`, which, in the same transaction, locks the waiting Tasks on items that now have no open blockers and queues their next run (`initial` with no runs yet, else `continuation`). Retries of Tasks with existing runs and replies aren't held back; retrying a cancelled Task with no runs rechecks blockers (see Retry admission).
- **Concurrency group:** a step's `concurrency: { max, waiting }` (`step_definitions.concurrency_json`) limits its Tasks on one work item. The group is the step key on the work item, so every version of the step and every way its Tasks start (`POST /tasks`, default assignment, an automation, a pipeline visit) share it. `TaskGroup` (`task/application/task-group.ts`) runs under `pg_advisory_xact_lock` on (project, work item, step key). `arrive` decides, with the arriving version's limit, whether a new Task is admitted (created as usual), waits (created `waiting_for_concurrency_slot` with no run) or is dropped (not created). Every Task of the group that hasn't ended holds a place, including one `waiting_for_person` or `waiting_for_work`. A drop is `ConcurrencyGroupFullError` (`Scarn.ConcurrencyGroupFull`): `POST /tasks` answers 409 with `meta: { stepKey, heldBy }`, an automation's step target is skipped (activity outcome `skipped: concurrency group full`), and a pipeline visit fails with it (engine event `task_dropped`), which `.catch` can take. `onTaskEnded` calls `ended`, which admits the oldest waiting Tasks into the places now free, with the limit of the step key's latest active version (`TaskEntity.admit`: `queued` with run #1, or `waiting_for_work` on a blocked item). A waiting pipeline visit's Task has no run to carry its base branch, so `ended` asks `TaskPipelineRunPort.findVisitBaseBranch`, which works it out from the run as the engine did on entry (`visitBaseBranch`); like a visit that's admitted straight away, it doesn't wait for blockers. Automatic retries and continuations are runs of a Task that already holds its place; manual retry of an ended Task reacquires a place (see Retry admission). Only a new Task (including a rerun's) arrives. Prompt Tasks and steps without `concurrency` skip the group. The claim query is unchanged: a waiting Task has no run to claim.
- **Previous run:** derived, not stored (`previous-task-run-id-sql.ts`): the same Task's run `number - 1`, or for a Task's first run the highest-numbered run of `tasks.previous_task_id` (a rerun). The run contract, the visit thread and the worker context still expose it as `previousTaskRunId`. Following it gives a run's chain, the step's history, which the worker context and the visit thread read (`DrizzleTaskRunHistoryReader`).
- **Turns:** `tasks.max_turns` is the step's effective `maxTurns` (default 2), copied when a step visit creates the Task. A standalone Task copies its step definition's optional `maxTurns`, else `DEFAULT_STANDALONE_MAX_TURNS` (20; prompt Tasks too). When a person replies to (or continues) a standalone Task whose queued continuation would leave it no turns, `TaskEntity.grantTurn` raises `maxTurns` by one so a chat never gets stuck; a pipeline Task (one `taskPipelineRun` finds) keeps its node's limit. Turns left (`turnsLeft`) is `maxTurns` minus the Task's `continuation` runs. When a run yields with no turns left, `onRunEnded` (`TaskEntity.followRun`) fails the Task with `Scarn.MaxTurnsExceeded` instead of making it wait.
- **Automatic retry:** the Task owns its retry policy (`retryJson`, a list of `{ on, maxAttempts }`). When a run fails, times out or is abandoned, `onRunEnded` names its error (`namedRunError`: `Scarn.Timeout`, `Scarn.HeartbeatTimeout`, else the run's reported `name`, else `Scarn.StepFailed`) and asks `retryDecision(retryJson, error, attempts)`, where `attempts` is the Task's earlier runs that failed (yielded runs don't count). The first entry whose `on` matches (or `Scarn.All`) allows `maxAttempts` retries. A retry is a new run (`reason: retry`, next `number`, the first run's base branch, the same input, a fresh session), the Task goes back to `queued`, and `taskOutcomePort` hears nothing. Otherwise the Task fails with the named error and the port is told. A yield past `maxTurns` isn't a failed run, so it is never automatically retried.
- **Manual retry:** `POST /tasks/:taskId/retry` (`executions:write`) retries a failed or cancelled standalone Task in place, including code Tasks that failed. The required body is `{ expectedLatestRunId }`, the latest run's ID or `null` when there have been no runs. A stale guard returns 409 `TASK_RETRY_STALE_RUN`; a non-retryable state returns 422 `TASK_NOT_RETRYABLE`. Pipeline-owned Tasks return 422 `TASK_RETRY_PIPELINE_OWNED`: rerun the pipeline instead. A cancelled Task may have a cancelled or yielded latest run, or no runs at all. The new run keeps the original instructions, execution config, input and first base branch; it does not use a newer step definition or restore the old session. Task outcome fields clear, but historical runs, errors and logs remain. The existing conversation reopens in `agent_turn` and can hand over again. Manual retry neither resets the automatic retry budget nor grants more turns.
- **Retry admission:** automatic retries and continuations keep the Task's held concurrency place. Manual retry of an ended Task must reacquire a place under the group lock, using the latest active step version's limit. A full group returns 409 `Scarn.ConcurrencyGroupFull` without deferring the Task or changing its runs or conversation. A cancelled Task with no runs rechecks work item blockers: it returns to `waiting_for_work` with `{ taskId, taskRunId: null }` while blocked, otherwise queues run #1 (`reason: initial`). A Task with runs queues the next `retry` run even if its work item has gained a blocker. A queued retry returns `{ taskId, taskRunId }`.
- **Task message:** a message a user sent to a step (`task_messages.task_id` is the Task it started). The history reader shows a Task's messages on that Task's first run. A run's messages are the messages on every Task in its chain.
- **Ending a Task:** when a Task succeeds, fails or is cancelled (a run ending it, **Done**, or a pipeline cancelling it, including a Task left waiting when its visit ends), `onTaskEnded` (`on-task-ended.ts`) closes its conversation and releases the saved session of every one of its runs (`releaseTaskRunSessions` in `task-run-sessions.ts`: clears `session_object_key` and `session_size_bytes`, takes the bytes off the org's usage meter and collects the keys). The transaction's owner deletes those sessions after commit (`delete-task-sessions.ts`, best effort). A succeeded agent run of a Task with no result schema stores `{ conversationId, summary }` (the trimmed summary it reported), opening the conversation if the agent never handed over, and its summary is posted as the closing agent message when it isn't empty. When a succeeded agent Task with no result schema closes a conversation a person spoke in, `onTaskEnded` also posts one work item comment (`author_kind` `agent`, `authored_by_task_id` the Task, whose name is shown as the author): its last agent message plus the branch of its latest run with one. A Task that never talked to a person posts none.
- **Stopping a Task:** `cancelTask` (`cancel-task.ts`, `POST /tasks/:taskId/cancel`, `executions:write`) ends an agent or MCP tool Task `cancelled`: a waiting Task ends directly, otherwise its open runs are cancelled and `onRunEnded` ends it. A pipeline step's Task is stopped by cancelling its whole run through `TaskPipelineRunCancelPort`, which the route implements with `cancelPipelineRun`; `tasks/` never imports pipeline code. Code Tasks (`TASK_CANCEL_CODE_TASK`) and ended Tasks (`TASK_ALREADY_ENDED`) are refused with 422.
- **Continuation:** a run whose `reason` is `continuation`, or a run with a message of its own. It gets its previous run's findings and transcript and starts its work branch from a yielded previous run's branch, else the nearest succeeded run in its chain. A Task without either starts from the upstream branch but still sees the chain's messages.

## Results

A Task holds its own outcome; there is no separate results table. `completeClaimedTaskRun` stores `status` (`succeeded` / `failed`), `resultJson`, `errorJson`, `workBranch` and `createdFromBranch` on the Task, resolves the artifacts its result declares, and creates the user notifications the result asks for, all in one transaction. It does not advance a pipeline: the API calls `completeTaskAndAdvance` in `pipeline-executions/`, which wraps it.

`yieldClaimedTaskRun` records a yield the same way: status `yielded`, `workBranch`, `createdFromBranch`, `sessionObjectKey`, `sessionSizeBytes` (the size the worker uploaded) and `sessionRestored`, and it archives the log so a continuation can read the transcript. A Task keeps only its latest run's session: the yield releases the sessions of its other runs (`releaseTaskRunSessions`), and an attached session publishes `SessionSaved`, which meters one write plus its bytes (`RecordUsageOnSessionSaved`; over the storage cap it records the write alone, and the daily reconciliation counts the stored size). It resolves no artifacts, and its only notification is the hand-over's. The API calls `yieldTaskAndAdvance`, which advances the run with `task_waiting` carrying the yield's `message`, or `task_failed` (`Scarn.MaxTurnsExceeded`) when the yield had no turns left.

- **Kinds and runs:** each kind has its own run entity (`task-run/entities/`): `AgentTaskRunEntity`, `CodeTaskRunEntity` and `McpToolTaskRunEntity`. An `mcp_tool` Task always has a result schema (the tool's output schema, or the built-in MCP content result `{ content, structuredContent }`), never yields, and completes through the same `completeClaimedTaskRun` as a code Task. The worker context carries `task.toolCall` only for this kind. A failed call reports a built-in error name (`Scarn.ArgsError`, `Scarn.McpToolError`, `Scarn.McpUnavailable`, `Scarn.McpOutputInvalid` or `Scarn.Timeout`), which `namedRunError` passes to the retry policy. See `docs/adr/0014-mcp-tool-steps.md`.
- **Artifacts:** a result-schema field marked `"x-scarn-artifact": {}` names an artifact. On completion each such field (outside arrays) becomes a `task_artifact_resolutions` row keyed by `(task_run_id, result_path)`, pointing at the uploaded artifact or recording why it couldn't be resolved.
- **Failing Tasks no worker will report on:** `failTimedOutTaskRun` stores `TASK_TIMED_OUT` once the Task passed its execution deadline; `failAbandonedTaskRun` stores `TASK_ABANDONED` once its lease lapsed. Claims and heartbeats find these Tasks and fail them through injected `TerminalTaskRunHandlers`, so the pipeline side can advance the run in the same transaction. `plainTerminalTaskRunHandlers` only fails the Task.
- **Clocks:** `heartbeatSeconds`, when set, is the lease every claim and heartbeat gets regardless of what the worker asks for. `executionTimeoutSeconds` is the deadline from the first claim.

## Branches

`baseBranch` is the branch the Task's work branch starts from; whoever creates the Task sets it (the pipeline engine picks the nearest upstream work branch, or null). The worker context reports `baseWorkBranch` as the continued branch of a steered Task (see below), else `baseBranch`. A finished Task reports `workBranch` (the branch it committed to, or null) and `createdFromBranch`.

## Previous runs and messages

The Task stays pipeline-unaware, so the pipeline sets the link: a retry or continuation is another run of the visit's Task, and a rerun's new visit gets a new Task whose `tasks.previous_task_id` is the old visit's Task (when both have the same kind), so its first run follows the old visit's latest run. Fresh visits, including visits downstream of a rerun, and standalone Tasks (`POST /tasks`) leave it null.

Sending a message (`POST /pipeline-executions/:id/visits/:visitId/messages`) reruns the visit and attaches the message to its new Task, in one transaction. It is rejected for code and MCP tool steps (`PIPELINE_RUN_MESSAGE_CODE_STEP`). `GET /pipeline-executions/:id/visits/:visitId/thread` lists the visit's runs and their messages.

The worker context (`task-worker-context-steering.ts`) puts every message in the chain into the prompt, with the attempt each one started. A continuation also gets `previousRun`, and the worker writes `.scarn/previous-run/findings.json` and, when the previous run's logs can be read, `transcript.txt`. That directory is never committed to the work branch.

Replies to a yielded Task are conversation messages, not task messages, so a continuation queued by a reply has no message of its own. A yielded previous run with a work branch is continued from that branch, and the prompt says it has no findings. For a `continuation` run, `task-worker-context-conversation.ts` finds the conversation through the previous Task's agent message, delivers its pending person and system messages to this Task (`deliverPendingMessages`, which locks the conversation and gives the agent the floor), and reads it back. Fetching the context again reuses the messages already delivered to the Task. When the yielded Task saved its session, `restoreSession` carries its download URL and a message built from what was delivered ("Reply from alex: …", oldest first, or the no-answer text for a continue without a reply). The fallback prompt lists "The conversation so far, oldest first": agent and person messages, the newest kept within 40,000 characters. Only a `continuation` run restores a session; a retry, rerun or steer starts a fresh one. The worker context's `task.turnsRemaining` is the run's Task's turns left (`turnsLeft`: `maxTurns` minus its continuation runs up to this run, null with no `maxTurns`): how many more times the agent may hand the conversation over. The prompt's turn guidance (`task-worker-context-turn-guidance.ts`) says when to hand back and how many times it can, and is left out at 0 or outside a run. A step with no result schema is a conversation step: its prompt has no findings section and its guidance says to call `scarn-end-conversation` when the conversation reaches its goal.

## Task execution config

The repo's config comes first; Scarn stores only the overrides. Step definitions and Tasks have a nullable `task_execution_config_id`: null means "run with the repo config as is", and a config with every field empty is stored as null, not as a row.

Rows are immutable and deduplicated per project on `(project_id, content_hash)`. They have no key, version or name. Pushing a step with the same inline config reuses the row; changing it points the step at another row. A Task created from a step points at the step's row (nothing is copied). The step API keeps its flat inline fields (`executionMode`, `envJson`, `repo`, `opencodeMcpJson`, `healthChecksJson`, …); `resolveTaskExecutionConfig` turns them into a row and the contract mapper flattens it back.

The entity enforces the cross-field rules on the server, since not every caller goes through the SDK: the git mode must fit the runtime, an env var's or health check's `mcp` names a server in the config, and an MCP-owned env var applies to the agent only. The stored JSON is versioned by `schema_version`; see "Changing stored JSON" in `docs/ddd.md`.

`TaskRunEntity.status` derives `timeout` and `abandoned` from the Task's own lease and deadline clocks, so plain repository reads report the live status; `persistedStatus` is the stored value. Reads never write.

## Not built yet

- The worker does not report agent sessions. `AgentSession` has a domain object and repo only.
- Tasks are only created from step definitions. There is no standalone Task from a raw prompt.
- Messages can't be sent to code or MCP tool steps. There is no queueing, forking or cancel-then-steer.
- `assertValidPreviousTaskRun` (same project, work item and kind) exists but nothing calls it yet.

Do not place pipeline definitions, pipeline run state or advancement in this domain.
